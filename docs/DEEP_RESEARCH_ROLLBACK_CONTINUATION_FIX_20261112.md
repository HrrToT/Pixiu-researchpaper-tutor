# 回退开关与继续研究入口修复

设计第17.2节要求回退关闭新运行入口、保留旧引擎归属及报告读取。检查发现公共创建接口遵守开关，但生产 RuntimeFacade 的内部 create 没有检查开关：从已完成结果“补查缺口”进入的 continue 可以绕过入口创建子运行。状态接口也仍返回 continue 动作。

## 最终行为

- `DEEP_RESEARCH_V2_ENABLED=false` 时，生产工厂的直接 create 和新 continue 均返回 `engine_unavailable`/503。新 continue 在领取操作回执之前拒绝，不创建子运行或留下失败回执。
- 开关关闭时状态投影移除 continue；既有报告、来源读取和运行控制仍使用原引擎。开关重新打开后，原未提交请求可以正常创建子运行。
- 已完成的 continue 回执继续按原负载指纹返回已有结果；同 requestId 不同负载仍冲突。待定回执保持 unknown_action，失败回执返回已保存错误，不重发。
- 运行时关闭后，在相同隔离SQLite上以关闭开关重新初始化，已存运行、合成历史报告正文和版本保持可读；新子运行仍被拒绝。
- 不修改原数据库记录、模型请求格式、预算或旧请求身份。promptVersion保持`.430`，因为此修复仅控制生产入口和状态投影，没有改变提示词；加载状态须按源码提交另行判断。

## 验证与边界

修复前：正确状态夹具下2项入口测试失败、4项已存回执测试通过；新增状态动作测试也确认continue仍被暴露。最初一次夹具错误跳过了合法状态转换，记录保留，不算产品失败证据。随后修正夹具为queued→running→completed。

最终7个关联模块57项通过，0失败；覆盖生产工厂、引擎分派、运行时、未知恢复、操作回执及离线完整研究链路。生产工厂使用独立SQLite，模型与业务发布使用离线夹具，没有付费模型、外部论文发送或生产数据库写入。证据见 `deep-research-evidence/rollback-continuation-20261112.json`。

本轮没有重启当前用户服务或切换其开关；这是候选源码与隔离运行时的验证，不是完整线上回退演练。此前Java成果保护候选仍未替换用户服务。完整DR0—DR5、真实研究内容和最终发布/回退验收继续保持未完成。

同轮官方余额只读查询返回 `is_available=false`、CNY `-0.19`。没有发送模型请求或重试旧案例。余额证据见 `deep-research-evidence/provider-balance-after-offline-20261112.json`；后续真实模型验证仍需账户恢复可用，原验证授权不变。
