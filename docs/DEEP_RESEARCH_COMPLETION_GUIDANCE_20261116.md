## 2. 为什么耗时，如何纠正

| 问题 | 已观察到的后果 | 执行调整 |
| --- | --- | --- |
| 答案遗漏、错归因与核验误拒同时存在 | 采纳数量不能说明哪一层错 | 先审完整答案，再分为取证、生成、核验、发布四类 |
| 来源身份、模型字段和显示标题分别表达 | 模型承担程序可确定的映射，协议容易漂移 | 程序维护论文/版本/表格身份，模型负责解释和综合，审核与显示共用结构 |
| 输入容量、修订预留、截止时间分阶段考虑 | 前面完成、后面无法核验或修复 | 调用前检查整轮，包含最终审核和一次有界修订 |
| 持续增加字段、提示和压缩封装 | 理解成本、模型负担及回归面增长 | 先消除重复和职责混杂；新协议须用保存样本证明收益 |
| 历史状态不断堆叠 | 最新结论难找，旧通过标记过期 | 唯一验收文件顶部突出当前门槛，历史作为链接 |
| 长期围绕相同论文调试 | 难以证明泛化 | 开发集用于定位，独立 H1—H6 用于验收；参与调试的留出案例退出留出集 |
| 全量、重启、环境恢复打断主线 | 反馈周期长、成果停滞 | 局部先测，稳定候选再全量；环境问题有界诊断，不扩大重构 |

不能把所有失败归因于模型，也不能为了通过而放松来源、数值、权限、预算和语义支持检查。

## 3. 固定边界

- 完成 DR0—DR5：方向调研、比较、主张核查、实验方案、研究切入点，以及任务材料/外部资料、追问、保存编辑找回、取消恢复、发布回退。
- 不重新加入旧项目导入、完整新手流程、独立 Edge 恢复。
- 不用 Qoder，不新开代理、线程或工作树；共享前端任务按文件归属隔离提交，对接成果结构和交互。
- 已授权材料和当前 DeepSeek 验证直接执行，不反复询问相同授权；新增范围按实际权限处理。
- 真实开发案例限 18 次调用、100,000 Token、360 秒，每次独立留痕，不自动重试。改变产品预算须明确提出。
- 不在收尾阶段替换整套编排框架或新建通用 Agent 平台；仅考虑明确减少阻塞且能隔离验证的组件。

## 4. 剩余工作包

主线 P0→P1→P2→P3→P5；P4 的静态检查和接口核对可提前，真实成果闭环在 P1/P2 后完成。每包交付必要源码、有效检查、简短证据及独立提交。

| 顺序 | 工作包 | 退出条件 |
| --- | --- | --- |
| P0 | 收拢当前比较候选 | 完成作者行身份上下文、修复两项失败、实际保存输入回放通过；无已知确定性失败；稳定源码全量通过，已测/装载版本明确 |
| P1 | 完整真实比较 | 合格的 D2-BASELINE-COMPRESSION 后续尝试一次执行；双方机制和成本正确、简表含必要条件、建议回应问题、关键事实无错误、预算合规 |
| P2 | 可执行实验方案 | 先审归档完整流程，再完成 D3；对照、变量、共同基线、初始化、指标、预算和判断规则完整，建议与证据分明 |
| P3 | 独立内容验收 | 冻结源码/模型/配置，完成未参与调试的 H1—H6；外部发现及正文读取真实发生；逐项满足原设计硬门槛 |
| P4 | 产品闭环 | 实际成果显示、定位证据、追问、保存、编辑和找回贯通；不误标完成，与并行前端合流后检查受影响交互 |
| P5 | 发布准备 | 最终回归、发布/数据/回退验证、准确 PR；全部门槛有适用证据，关键失败已处理；通过前维持草稿，不合并 |

### P0 第一批动作

1. 已完成的身份映射、审核对象协议和联合示例路径保留，不重复建设；旧真实响应不升级通过。
2. 集成两项当前修复：同批确定解析失败不重复启动解析器，下一批仍可重试；生成前按账本两种已消耗调用计数分配草稿核验容量，预留生成、整答审核和一次修订。
3. 该分配只是调用资源安排，不能证明 Token/耗时足够。超额草稿完整保留在内部未核验状态，不能截断、发布、自动追加模型调用或删除用户要求来凑预算。
4. 保存响应回放已进入后续编译，10 点未核验，另 1 点因正文内部标签隔离。这是旧响应的生成问题，不把隔离结果说成完整答案成功。
5. 当前局部检查通过后提交并冻结源码，做一次集成全量；装载身份、原服务恢复及新尝试唯一留痕齐备后才执行一次真实比较。若解析再失败，读取新增安全错误类别诊断，停止重复猜测环境。

### P2 实施原则

共同基线、变量、共享状态及阶段规则只声明一次，各组引用并说明差异。先保证科学方案可执行，再决定结构字段。避免让模型同时做研究构思、重复填写大型配置和复杂压缩解码。

先用保存样本检查完整调用链和预算，再修改必要层次；不先创建通用实验语言。不能靠删除对照、初始化、边界或判断规则满足容量。若预算不可行，提交容量证据与产品取舍，不继续无界压缩。

## 5. 每轮执行规则

开始前写五项：完整用户结果、当前失败、根因假设、修改层次、能推翻假设的检查。一个迭代处理一个主要根因，必要的跨模块修改一起验证。

1. 保存样本复现：定位输入不足、生成错误、核验误拒或发布丢失。
2. 受影响模块及相邻接口检查；增加能区分正确/错误行为的正反例，避免实现镜像测试。
3. 整轮输入、调用、Token、耗时准入检查，含最终审核及修订余量。
4. 稳定候选一次全量，期间不编辑 Python 源码。源码未变且已通过时不重复同一全量。
5. 一次真实案例，先看用户最终结果，再查事实、条件、来源及账本。内容通过、内容未通过、证据不足、运行未知分别记录。

同类失败经过两个真实修复迭代仍未改善完整成果，停止第三次同类提示微调。产出一页结构诊断，在证据组织、任务拆分、职责划分、核验、发布中选择必要层次修正。不能仅改编号、扩上下文或加规则继续试。

真实验证准入：无已知确定性失败；全量适用当前源码；装载身份明确；案例可执行、无未知请求重放；整轮预算可行；原始结果和恢复路径已准备。准入保持简短，不再建设一套框架。

关键条件缺失时，局部事实通过不能算完成。正常停止与质量通过分开；正确表达证据不足，不能替代本应完成的研究能力。

## 6. 效率与协作

- 同时只推进一个主要内容阻塞。独立界面检查、文档、环境诊断可穿插，不让多个半成品协议一起扩张。
- 不因每次小改就重启、全量、付费复测。服务恢复根据运行证据执行；已知 Windows asyncio 环境故障采用已验证环境，不反复长等 socketpair。
- 未知请求冻结并核对账本，禁止自动补发。已结算案例可用新尝试复测，未知案例不得换名重跑。
- Git 显式暂存本任务文件，按可审查行为拆提交；不收集共享前端脏文件和大量无关历史产物。
- 基础设施、协议、科学内容分别定位，最终交付仍以完整用户任务判断。

## 7. 进度与结束口径

唯一验收状态为 DEEP_RESEARCH_ACCEPTANCE_STATUS_20261015.json。本方案只负责顺序。顶部明确当前源码、最近全量源码、装载版本、未通过门槛、下一动作；历史字段不得冒充当前状态。逐步整理摘要，不先重写庞大历史记录。

每轮只汇报：完整能力是否改善、关键证据、主要阻塞、下一判断、新增真实调用、剩余门槛。不用提交数、测试数或累计运行时间估算完成百分比。

目前不能可靠承诺剩余几天。P1 后测得完整内容迭代周期，P2 后再按剩余门槛评估工期。区分主动开发、测试/服务等待和会话累计时间，不能混称集中开发日。

结束标准仍为原设计第 19 节：关键事实无严重错误、条件完整、来源权限正确、预算恢复合规；目标回应、证据支持、条件完整、综合价值、可执行性、可读性达到要求。离线、真实 Provider、独立内容、产品闭环分别记录。已有适用证据复用，无须无意义从头重测。

当前从 P0 集成收口进入 P1。局部编译改善不计独立科学验收；P1—P5 退出条件保持，不以测试数量代替成果质量。
