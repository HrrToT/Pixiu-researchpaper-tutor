## 2. 开发为什么拖长

| 问题 | 已观察到的影响 | 接下来的调整 |
| --- | --- | --- |
| 多维比较压进少数大段结论 | 一处来源、数字或表述错误可能使整段比较不可用 | 按论文×维度形成独立事实条目，分别核验，服务端组合表格 |
| 围绕同一批真实案例持续局部修补 | 传输和修订变可靠，但完整成果仍不合格 | 每个迭代先定义要改善的完整输出；同类失败两次后停下诊断结构 |
| 模型同时承担事实、格式、身份映射和复杂协议 | 输入冗长，失败原因混在一起 | 程序负责来源身份、格式、计数和状态；模型负责理解、综合与语义判断 |
| 合成结果与最终显示结果之间存在差异 | 审核对象与用户看到的答案可能不一致 | 生成、事实核验、整体覆盖审核、发布共用同一份结构与显示契约 |
| 验证记录数量容易掩盖成果状态 | 离线通过、调用成功、内容通过被误读成同一件事 | 用一张当前验收表展示三者，历史明细保留为链接 |
| 每次微调都可能触发广泛回归和环境恢复 | 反馈周期变长，注意力转向基础设施 | 局部改动先跑相关检查，候选稳定后跑全量；基础设施单列问题 |

这是对开发方法的纠正。不能将所有失败归因于模型，也不能为了提高通过率删除科学条件、放松来源核对或把空结果称为成熟能力。

## 3. 固定边界和取舍

完成目标仍包括：方向调研、论文比较、主张核查、实验设计、研究切入点；任务材料与外部文献两条路径；追问、成果保存编辑和找回；取消、恢复、预算及发布回退。

保持原有授权、预算和用户豁免。旧项目导入、完整新手流程和独立 Edge 恢复不重新加入。开发不用 Qoder，不新开代理或线程；共享前端任务的文件不纳入本任务提交。

收尾期间不新增通用 Agent 平台、第二套编排引擎、模型自动选择平台或开源整包替换。既有适配器能够复用的组件优先复用；只有明确缺失、可隔离并能减少当前阻塞的能力才引入依赖。复用框架不能代替论文证据和内容验收。

## 4. 按完整成果推进的工作包

| 顺序 | 工作包 | 交付和结束条件 | 失败时的动作 |
| --- | --- | --- | --- |
| A | 收拢当前比较实现 | 补齐最终布局进入整体审核、字节预算和答案身份；提交当前呈现改动；定向检查及一次稳定候选全量检查通过 | 对照生成结构与审核输入查缺口，不先改科学判定 |
| B | 完成真实论文比较 | 通过服务端受控配置创建新运行；D2 新案例一次提交；得到可读简表、各论文证据与条件、可比性判断和有条件建议；逐项对照原文 | 定位证据不足、生成错误、误拒绝或发布错误，修对应层；不扩大预算掩盖问题 |
| C | 完成实验方案 | 先用归档输入审查端到端调用与输入容量，再实现最小必要的共享方案/分阶段配置；D3 一次真实验证；对照、变量、初始化、指标、预算和判断标准完整且可执行 | 若科学方案本身不成立，先修方案；不继续堆字段格式规则 |
| D | 冻结并做独立验收 | 固定提交、模型和配置，执行未参与调试的 H1—H6；真实外部发现和全文阅读须真实发生；内容、预算、可靠性分别记录 | 失败用例退出留出集；修复后用同类新案例验收，保留原失败 |
| E | 产品闭环与并行前端合流 | 实际生成成果在界面正确呈现；能定位证据、追问、保存、编辑、再次找回；验证状态不误导；核对共享前端变更 | 只修实际阻碍任务的交互，不扩大视觉改版范围 |
| F | 发布准备 | 对最终提交完成受影响层检查与全量回归，确认数据/发布/回退；PR 描述准确列出范围、证据和限制 | 未满足原设计硬门槛则维持草稿，不以局部通过发布 |

依赖主线为 A→B→C→D→F；E 的清单和隔离界面检查可提前进行，真实成果验收在 B/C 后补齐。B/C 内涉及其他研究类型的底层缺陷必须一并修正，不声称这两类通过就覆盖所有类型。

### A 的具体交接点

1. 保留当前已通过的 48 项局部检查结果；只对后续新增改动补测。
2. 将服务端比较布局作为可信显示元数据带入整体覆盖审核，参与请求容量计算及当前答案身份绑定。元数据只能说明如何呈现，不能作为论文事实或自动通过依据。
3. 审核和发布均使用当前已核验条目；被拒绝的内容不能从草稿或布局元数据重新进入正文。
4. 默认开关保持关闭；用相同生产依赖、受控服务端配置验证新路径，不通过客户端绕过规则，不改变历史运行策略。
5. 新路径整体可测后，运行一次覆盖当前源码的全量检查，再进入 B。不要引用 aff24567b 的旧全量结果替代。

### C 的架构原则

实验方案先表达科学问题和可执行关系，再编码详细配置。共同基线、变量、共享状态和阶段规则只声明一次，各实验组引用它们并说明差异。生成前计算整轮最坏调用数量、输入大小及保留的核验容量。

需要用实际请求样本验证是否可在现有 18 次调用、10 万 Token、360 秒限制内完成，不预设“拆得越细越可靠”。禁止靠删掉对照、条件和来源满足容量。若仍无法容纳，先减少重复表达和不必要阶段；改变产品预算须另行明确，而非静默增加。

## 5. 更短的开发反馈周期

每个迭代只处理一个主要失败类别，并在动代码前写出：当前失败、根因假设、拟改层次、能推翻假设的检查、期望用户结果。

验证顺序固定为：

1. 已保存输入/输出的离线复现：先证明定位正确，不新增模型调用。
2. 受影响模块与相邻接口检查：来源、数字、预算、终态保护按实际影响选择；不为可逆文案改动写实现镜像测试。
3. 完整候选检查：涉及执行协议、核验和发布等关键链路的候选，在真实验证或发布前跑一次全量；源码冻结期间不继续修改。
4. 一次真实案例：必须经过实际生成、核验和结果路径，保存原始响应、费用和输出。不自动重试；修复后复测另记新案例。
5. 审查最终成果：先看回答是否解决原问题，再查关键事实和条件；调用成功、JSON 合法和测试数量均不替代这一步。

同一失败类别经过两个真实修复迭代仍未改善完整成果时，停止第三次同类微调。产出一页根因判断，比较证据输入、任务拆分、生成结构、核验误判、发布丢失等解释，选择一次结构性修正。该规则限制重复修补，不限制必要的后续质量验证。

不预设核验器永远正确。每次零采纳或大量拒绝，抽查全部关键被拒条目，区分真实错误与规则误拒；误拒通过通用规则和反例修正，不能按论文名称或案例编号放行。

## 6. 进度和记录方式

进度以已通过的产品门槛描述，不再用模块数、提交数、模型次数或测试增长估算完成百分比。对外汇报只保留：

- 本轮完成的用户能力及对应证据。
- 当前唯一主要阻塞和下一步判定。
- 尚未通过、尚未测试的范围。
- 新增真实调用和预算，必要时说明运行版本与源码差异。

沿用当前验收状态文件，不再建立相互竞争的进度真源。每次候选保留一个简短汇总链接到原始证据；历史运行、失败与未知请求保持原样，不向完整设计稿头部继续堆叠日常日志。

每个工作包交付独立且可审查的提交，源码、必要测试和对应证据一起提交；只显式暂存本任务文件。共享前端任务的改动在合流时单独核对。独立验收失败不能只更新“完成率”，必须标明哪个能力未通过。

## 7. 本次复盘后的第一步

先执行 A：补齐“最终比较布局→整体审核→发布”的一致性，收拢当前未提交实现。随后做一次真实 D2 验证，按完整成果决定下一步。此时不先启动另一轮实验字段修补、全量留出验收或基础设施重构。

结束标准仍是完整设计稿的实际验收记录，不承诺未经证据支持的剩余百分比或具体天数。A/B 形成稳定真实结果后，再按剩余工作包与已测反馈周期给出工期区间。
