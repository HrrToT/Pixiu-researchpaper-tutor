### 后续交付顺序与检查点

1. **完整比较**：冻结上述候选，相关检查通过后全量一次、装载一次、真实比较一次。验收双方事实、条件、综合取舍和建议；关键事实逐条人工核查，六项适用评分均至少4分。允许有依据地保留未知，不能用部分报告替代原比较要求。
2. **完整实验方案**：复用比较阶段已证明有效的调度和取证能力，检查四组对照、共同起点、变量、预算、指标、主效应/交互效应、步骤及局限。只改实验特有缺口，不同步重写比较架构。
3. **独立材料与产品闭环**：按设计§19盘点D1—D6/H1—H6现有证据，仅补不适用、缺失或因修复失效的项。新材料不参与本轮调参；联网必须证明实际发现和读取，缓存回放不替代。界面验收覆盖开始研究、读结果、定位证据、追问、保存、编辑、找回及重开。
4. **发布收口**：最终候选必要回归、装载与回退检查；更新使用说明和PR。满足原门槛后才退出草稿，不自动合并。用户已豁免的旧项目导入、完整新手流程、独立Edge恢复不重新加入。

### 提速纪律

- 一个主线候选、最多三个主要阻断；不同时开展多个架构改造。尊重并行交互任务文件边界，不启用Qoder或另开开发代理。
- 保存输入和响应先诊断，相关集验证修改，冻结候选才全量。文档/证据变化不跑全量，真实执行期间不改代码。已有9654项是保护基线，不以删除测试提速。
- 每次真实执行前写出“本次能验证什么”；失败后先核查第一失真环节。相同根因两轮无改善，停止提示补丁，做任务结构或固定输入模型对照决策；不自动启动下一次同题调用。
- 调度问题不交给提示解决，确定性身份/表格展示不让模型重复生成，语义问题不靠放松硬检查处理。必要模型对照仅比较固定输入的一处能力，不同时改模型和提示。
- 运行失败保留有效成果和准确限制；正常成功路径必须仍能完成原要求。避免通过把所有失败改为“部分完成”制造表面达标。
- Docker只用于装载及必要集成；环境失败单独记录，不在每次内容调试中反复重启恢复。当前原服务已恢复，无需再操作项目外目录。
- 每个交付点只维护候选、已过门槛、未过门槛、下一动作；历史细节留证据。按诊断、生产修复、验收结果拆有意义的提交，明确文件清单，不吸收共享脏文件。
- 估算下一交付点，不承诺整个项目固定天数或虚假百分比。比较和实验两条完整链路通过后，再依据剩余验收矩阵估算发布工作量。

## 1. 复审结论

现阶段主要瓶颈是完整答案质量，以及生成、核验、修订能否在预算内共同完成。工程保护应保留，但继续增加保护规则和测试数量，不能直接解决内容质量。接下来保留框架，集中修完整链路，不围绕单篇论文无限补丁。

当前证据：

- 源码05bc4831e完整离线回归9627项、498模块，0失败/错误/跳过，旧9600项保留。这是工程覆盖证据。
- D2-BASELINE-COMPRESSION-v13两阶段生成10条草稿，均通过结构编译；11次模型调用、63843账本Token、193秒，终态completed + inconclusive，没有通过最终核验的条目。这是开发集结果，不是独立验收。
- 原服务已恢复，全部当前任务、运行、调用一致，恢复没有新增模型请求。原始结果保存在本地tmp/dr-acceptance-receipts/，不公开论文正文和原始响应。
- 失败同时包含真实内容错误和疑似审核误拒：另一篇未报告数据的无依据断言、维度混写、引用不支持具体数字、磁盘体积与显存混淆，及版本身份、表格显示条件、审核诊断问题。疑似误拒尚待逐项确认，不能一概放宽。

证据：[完整回归](deep-research-evidence/comparison-source-stages-graph-full-20261118.json)、[候选装载](deep-research-evidence/source-stages-candidate-load-20261118.json)。当前状态统一维护于[执行状态](DEEP_RESEARCH_CURRENT_EXECUTION_20261117.md)，历史结果不逐轮复制进本方案。

## 2. 开发为何变慢，如何纠正

| 问题 | 后果 | 纠正 |
| --- | --- | --- |
| 节点局部通过后才检查下游 | 生成、审核、修订轮流暴露问题 | 一个候选验证生成到发布的完整链路 |
| 同题提示微调和真实重跑反复交替 | 成本增长，泛化未证明 | 保存响应先回放；开发集调试，独立集验收 |
| 模型重复填写机械信息 | 行号、身份、格式错误挤占推理 | 程序负责精确对象、数值与条件展示；模型负责解释和综合 |
| 所有拒绝都当答案错误 | 正确答案因审核故障被反复改写 | 区分真实错误、确定性误拒、语义审核问题、调度失败 |
| 只看总预算或调用下限 | 总量尚余但修订装不下 | 预演生成、审核、一次修订、复核及终审的实际路径 |
| 协议、证据、文档逐轮增长 | 当前状态过时，维护成本上涨 | 新运行只有一个当前入口；历史兼容集中边界；当前事实只维护一处 |
| 测试数量替代成果评估 | 工程通过掩盖内容不合格 | 以合格成果和剩余门槛报告进展 |

不推倒已有LangGraph、账本、权限、恢复与来源分阶段实现；本轮不增加编排框架、不重新拆服务、不迁移历史记录、不扩展功能范围。

## 3. 首批交付：诊断闭环，不立即付费重跑

1. **十条草稿人工判定表**：逐条列出目标、引用、原文支持程度、程序拒绝原因、人工判断、首个失真环节和修复归属。模型拒绝理由只是待核查信息。
2. **核验器正反例回放**：保留原坏答案，另给人工确认的正确表达，经真实生产节点检查；分别看正确事实能否通过、错误事实能否拦截。受控正确表达不算生成质量通过。
3. **实际修订容量图**：用原请求和账本解释未发送批次、空修订、输入窗口不足，记录输出预留、剩余调用和时间。调用次数下限不等于全路径可完成。
4. **一次实施决策**：按证据输入、任务分工、确定性展示、语义审核、调度分类，最多保留三个主要阻断，合并相互依赖的修改后再出候选。

本批不新增真实模型请求、不重跑全量。出口是每项拒绝有分类、疑似误拒有最小正反例、下一批修改有完整成果上的验证目标，不另建抽象诊断框架。

## 4. 待诊断确认的修改方向

| 优先级 | 方向 | 边界 |
| --- | --- | --- |
| P0 | 单论文事实与跨论文综合分工 | 单论文阶段回答自身证据；跨论文缺失判断交由综合阶段依据可见材料处理。不靠删除坏句子伪造正确 |
| P0 | 精确测量由程序展示 | 复用V引用与表格绑定呈现来源、方法、数据组、指标和单位，模型解释取舍；正文与导出都可读懂条件 |
| P0 | 修复有证据的审核误拒 | 版本来自可信来源元数据，不能来自用户问题；中文显示只允许有正反例覆盖的窄范围等价；事实和条件门槛不放宽 |
| P1 | 修订调度保留有效结果 | 只修真实错误；审核故障不诱导改写正确事实；发送前保留复核与终审容量，不静默删维度 |
| P1 | 小范围模型能力对照 | 材料、任务和审核合理后仍持续误读，才用固定输入比较当前模型与一个可用候选 |

这些是候选方案，不是已经证实的根因。优先复用现有领域对象，避免平行协议；只有持久化或兼容语义确实改变才增加版本，不为每次提示变化新建整套契约。

模型对照先只读核对实际调用模型与可用模型，不依据GUI名称推断。生成和审核分别比较，同输入、同任务、同输出要求，不同时改变提示与模型；人工判断关键事实、覆盖、可读性，记录调用、Token、耗时和可得费用。每案例仍限18调用、10万Token、360秒，一次提交，无自动重试。对照只决定开发路由，不冒充完整案例或独立验收；若明显改善，只给困难综合或核验使用较强模型。若无改善则返回材料/分工，不开展多模型试用。不使用Qoder。

## 6. 验证纪律与停止条件

固定循环：**保存结果回放 → 相关单元/集成检查 → 完整结果与容量审查 → 冻结候选 → 一次全量 → 装载核对 → 一次真实案例 → 人工验收**。

- 开发中跑相关集；稳定候选才全量。文档、证据摘要变化不重跑全量；全量和真实案例期间冻结源码。9627项作当前基线，不删有价值保护来提速。
- 一次真实失败先离线归类。相同根因两次修改仍无改善，停止该修补方向，做一次任务结构/模型能力决策，不能直接开始下一轮同题复测。
- 人工确认的正确表达也被稳定拒绝，先修核验器；正确对照能过而模型反复编造，改生成分工/模型，不放宽审核。
- 新失败未改变主要根因时，纳入同一交付批次，不为每条措辞单独开补丁和全量。严重权限、数据或账本错误立即处理。
- 未知请求保留原身份和预留，不重发、不换名绕过；不扩大为整个项目无法继续。
- Docker仅用于装载、运行和必要集成；离线使用已验证环境，不重复做没有新证据的环境恢复。
